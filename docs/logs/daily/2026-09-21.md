# 2026-09-21 — motion-energy notebook rebuilt for GISLR_Stratified, run, analyzed

`gislr.0.dataset.motion-energy.ipynb` (TODO §1) went from "deleted, broken by
the 2026-09-16 dataset migration" to a rebuilt, run, and written-up result in
one day.

## 1. Build

The pre-npz version (raw `asl-signs` parquet via DuckDB) was deleted
2026-09-19 when it broke on the GISLR_Stratified npz move; this rebuild reads
npz directly, no DuckDB needed (there's no 94K-file JOIN to push into SQL once
metadata is two CSVs). Three changes from the original, closing TODO §1.8 and
partially §7.7:

- **z dropped before the speed computation**, not decomposed after — every
  scope computes `rms_speed` directly on xy. The 2026-07-15 report's finding
  (92% of pose "motion" was z-noise, on a 50-video sample) motivated
  measuring xy natively rather than as a post-hoc split.
- **Savitzky-Golay smooths the position series before the frame-to-frame
  difference** (unchanged window=7/polyorder=2) so jitter is removed before
  the derivative sees it, not filtered from the RMS afterward.
- **New: 28 joint angles' rate of change** ("change of angles", RMS angular
  speed in deg/frame), reusing `sb.recognize.interp.kinematics.compute_angles`
  rather than re-deriving joint geometry.

New shared code in `sb.recognize.interp`: `motion_energy.py`
(`landmark_motion_energy`, `joint_angle_motion`); `reindex_interpolate` and
`smooth_savgol` promoted out of `kinematics.py`'s private functions into
shared `geometry.py` so the two pipelines can't drift on what "filled" and
"smoothed" mean. Verified end-to-end against real npz data (all three scopes,
manifest resume, streaming global aggregation, cross-scope comparison) with a
throwaway cache before handoff — caught one real bug this way: `plt.show()`
blocks on a GUI event loop outside a notebook kernel, which is why the first
verification pass looked hung for 40+ minutes; switching to `MPLBACKEND=Agg`
for the test harness (not the notebook itself — Jupyter's own backend doesn't
block) confirmed the actual per-video compute is ~0.03s.

## 2. Run

The user ran the notebook end to end: 50 videos, 10 signs (≈3,662 videos),
and the full global scope (94,477 videos, 189 chunks) — **0 failed units**
across all three.

## 3. Findings (full detail: `docs/reports/motion-energy.md` §5)

**The xy-native global numbers confirm the 2026-07-15 sample-based estimate**
almost exactly: per-type detection rates reproduce to the decimal (99.9% face,
100% pose, 54.7% right hand, 41.4% left hand), and the pose-subgroup xy
magnitudes the old 50-video sample estimated land within ~15% of the new
94,477-video global numbers on every subgroup, exact on head/hips/arms. This
is independent, cross-dataset confirmation that seeded samples reproduce the
global landmark-motion ranking.

**New wrinkle, not resolved:** legs (0.0173 xy RMS) sit almost as high as
arms (0.0185) at global scale — the old keep/discard verdict dismissed legs
as "out of frame, apparent motion is jitter" on xyz grounds (95% z-noise);
the xy-native number doesn't fully support that on its own. Filed as a
follow-up for the discriminability instrument, not resolved here or treated
as a revision of ME-126.

**Joint-angle findings (new instrument):** shoulder/elbow angles change
fastest (arm-swing carries most articulation), thumb joints change least.
Right-hand angles exceed left in 13 of 14 paired joints — the same
dominant-hand asymmetry detection rate already showed, now visible in *how
much the joints move* — except the elbow, where **left** leads by the
largest margin in the whole 28-angle table, flagged as a genuine oddity
rather than noise. Cross-scope correlation also surfaced a new
methodological finding: a single-video sample is a much noisier estimate of
the global *angle* ranking (rho 0.743) than of the *landmark* ranking (rho
0.951) — angle-motion analysis should sample at the category level or
larger, not per-video.

## 5. Later the same day: registry audit + legacy-split deprecation

Asked to "port all outdated training regimes" to GISLR_Stratified and
benchmark every model type. **Audit finding: nothing needs porting** —
every training-producing notebook (`gislr.1.models.training.ipynb`,
`firstplace`, `landmark-importance`, `curated-features`, `bilstm-curated`)
already resolves the current split automatically. The 52-of-55 legacy-split
registry entries are old only because they predate the 2026-09-16 reset;
re-running the same cells now trains on the current split unchanged.
Documented as `TODO.md` §4.3, including the real gap (12 unrun cells:
`gru_deep`/`lstm`/`bilstm`/`cnn1d` × 3 subsets) and two open decisions
(1st-place port has its own unresolved collapse investigation; whether
`gru`×xyz is worth re-benchmarking given the settled xy-beats-xyz finding).

Declared the 52 legacy runs obsolete **without a schema migration** —
`dataset`/`split.n_val` already determine this permanently, so
`sb.mlops.registry.is_legacy_gislr_split` derives a `legacy_split` boolean
on read rather than persisting a new field to 55 `meta.json` files. Wired
through `index.csv` (new column + `--legacy`/`--current` CLI filters), the
README's generated leaderboard (excludes legacy by default — ranking two
non-comparable splits together was already misleading), `sb.mlops.query`
(`split_n_val`/`legacy_split` columns, `leaderboard(include_legacy=...)`),
and `sb.mlops.promote.check()` (now **refuses to promote a legacy-split
run** to any alias — closes a real gap; nothing previously stopped a
stale-split champion). Deliberately did **not** change `leaderboard()`'s own
default (`include_legacy=True`) — `gislr.2.models.evaluation.ipynb` picks
its top-N for learning curves/confusion matrices/**TFLite export** from it,
and flipping the default would have silently changed which checkpoint gets
exported.

## 6. Later still: BiLSTM-curated ablation run and analyzed

The user ran the 4-arm ablation built earlier this session (TODO §3.6) — 0
errors, decomposition sanity check passed exactly.

**Verdict: the curated feature set is the dominant cause of `bilstm_curated`
losing to `bilstm_base`, not the architecture.** Decomposing the −15.90pp
gap: **feature set −17.4pp** (more than the whole original gap on its own),
**architecture +10.6pp** (the attention gate + projection bottleneck
recovers over 60% of that loss — it is not the problem, it's protective),
**batch size −9.1pp** (real but secondary; training curves show
`bilstm_curated` reached the *lowest* train accuracy of the three curated
arms despite training as many epochs as `bilstm_curated_b1024`, consistent
with under-training from ~4x fewer gradient steps per epoch at batch 4096 —
not proven, filed as a follow-up). Even the best curated configuration
(`bilstm_curated_b1024`) still loses to `bilstm_base` by 6.8pp — the 922-dim
engineered feature set is a genuinely worse fit for a bidirectional LSTM
than the 252-dim raw pipeline here, not a config bug.

Side finding: `bilstm_base` (73.71%) sits *below* every current-split `gru`
run (74.25–75.17%) — bidirectionality buys nothing over the streaming
architecture once both are measured on the same split.
