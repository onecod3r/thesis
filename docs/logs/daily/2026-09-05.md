# 2026-09-05 — the plateau is a generalization gap, not a label ceiling

The GPU arms of the plateau diagnosis ran. Together with yesterday's CPU arms they close
TODO §7.1's central question, and the answer is not the one the confused-pair evidence
suggested.

Full write-up: [`docs/reports/plateau-diagnosis.md`](../../reports/plateau-diagnosis.md).

---

## 1. The result

**Semantically similar signs are not why accuracy stops at ~75%.**

| measurement | result |
|---|---|
| error mass in the top-20 confusable pairs | **10.5%** |
| accuracy if those were solved perfectly | 0.7433 → **0.7704** (+2.7 pts; random control +0.007) |
| symmetric confusion, **val** | 0.273 |
| symmetric confusion, **train** | **0.012** — 19 of 20 pairs at exactly zero |

The second half of that table is the decisive part, and it came from §7. The models separate
these pairs essentially perfectly on data they were trained on and fail to on data they were
not. **That is a generalization gap, not an ambiguity in the vocabulary.**

It also settles the tension sitting in §7.1: the 07-19 verdict (overfitting, train 90–99% vs
val ~75%) and the 08-23 note (label ceiling, because the confused pairs are near-synonyms and
replicate across architectures) could not both be the main story. The first one is.

## 2. What the landmarks carry — §8, and a correction to yesterday's speculation

A binary probe that only ever sees one pair, on time-pooled features:

- median 0.628 on a **binary** task; `awake`/`wake` at **0.463**, i.e. chance
- `corr(confusion_rate, probe_accuracy) = −0.72` — the pairs the models confuse most are
  exactly the ones a pooled probe cannot separate
- robust to method: standardisation and stronger regularisation move `awake`/`wake` 0.463 →
  0.464, so it is not a scaling artifact

I then added §8b to test the obvious follow-up — that the distinction is in *movement*, since
`awake` is repeated where `wake` is single. **Pooled velocity does not rescue it either**
(`velocity_gain` ≈ 0 or negative for 6 of 7 pairs).

The honest reading is narrower than "the landmarks lack the information". Pooling destroys
ordering and trajectory shape, which is precisely where these pairs differ. The sequence models
beat the probes (≈57% recall on `awake`/`wake` vs the probe's 46%), so they *are* extracting
temporal structure — it just does not survive to unseen signers. **This does not refute §7.3**,
which proposes per-frame velocity channels into a sequence model, a different claim from pooled
velocity summaries in a linear one.

Yesterday's report speculated that the diffuse error "points at §7.2 normalization". That
still holds, but for a better reason than I gave: not because the true label is often outside
the top 5, but because §7.2 and §7.4 are the two levers that attack a *generalization* gap
directly.

## 3. Consequences filed

- **§8 (rescoring layer) is bounded at ~2.7 points**, and only on the near-miss tenth of the
  error where the true label is already at rank 2 (77% of semantic errors). Worth doing on its
  own terms; not a plateau fix, and it should stop being described as one.
- **§7.2 normalization and §7.4 augmentation are the evidence-backed next levers.** Nothing in
  the stack currently removes signer appearance or position.
- **`finger`/`wait` and `animal`/`have`** are confused as heavily as the near-synonyms without
  being semantically related — and `finger`/`wait` has the *highest* probe score of the set
  (0.790). Whatever drives those is not meaning, and it may be the more informative case.

# 2026-09-05 (second) — the TypeScript extractor's first run: it cannot run

Separate thread, separate result. TODO §10.1 had the Deno extractor written,
typechecked and never executed, because `deno` and `ffmpeg` were absent. Both are
installed now, so it ran for the first time.

Full write-up: [`docs/reports/extractor-parity.md`](../../reports/extractor-parity.md).

## 5. The result

**0 of 12 clips extracted.** Every one:

```
ReferenceError: WebGLRenderingContext is not defined
    at _emscripten_webgl_do_create_context
    at Module._changeBinaryGraph
```

`_changeBinaryGraph` is graph *construction* — before a frame is submitted. Two
assumptions died with it:

- **`delegate: "CPU"` does not mean "no GPU work."** It picks the CPU inference
  backend; the web build's image pipeline is GL-backed regardless. No option
  turns it off.
- **`ImageData` was never the hard part.** The package chose Deno over Node
  because Deno has `ImageData` and Web Workers natively. True, and not the
  binding constraint. Deno has `ImageData`, `OffscreenCanvas`,
  `createImageBitmap` and WebGPU — and no WebGL at all. Node is no better
  placed: the requirement belongs to MediaPipe's *web* distribution, so it would
  need `headless-gl`, the native module Deno was chosen to avoid.

Three layers of misleading errors sat in front of that one — `document is not
defined`, then `require is not defined` (Emscripten sniffs `process.versions.node`
and Deno satisfies it), then `both async and sync fetching of the wasm failed`
(Emscripten skips `fetch` for `file://`). `src/dom_shim.ts` now keeps all three
solved **so the failure states the real constraint**, and says in its own header
that it is not a fix.

## 6. Two defects the attempt found on its own

Either would have produced a confident, meaningless parity number:

- **The geometry could never have matched.** TS hardcoded `scale=640:480 -r 30`;
  Python feeds cv2's native frames at the video's own rate. POPSIGN is
  **1944×2592 portrait** at 30 / ~29.92 / 120 fps, so the default inverted the
  aspect ratio *and* resampled time — frame counts off by up to 4×. `probe()`
  existed for this and had never been called. Geometry now defaults to per-clip
  native; the flags are overrides.
- **The two sides loaded different models.** TS defaulted to the bucket's
  unpinned `latest`, Python to the local `.task`. The comparison would have
  measured the model, not the code.

Also: `deno check` did not pass before today —
`Uint8ClampedArray<ArrayBufferLike>` is not assignable to `ImageData`'s
`ArrayBuffer` under Deno 2.9.6 / TS 6.

## 7. Repo changes

- New: `sb.extract.parity_run` — seeded selection → hardlink staging → both
  extractors → npz format check → `sb.extract.parity`, resumable throughout. A
  TS-side failure is a *result*, not a crash: the Python half still runs, so its
  reference tree exists for whenever the TS half can.
- New: `packages/sb-extract-ts/src/dom_shim.ts` (see above).
- `worker.ts` probes native geometry and rebuilds the landmarker on a resolution
  change — porting the Python extractor's `RET_CHECK ... current_mat->rows`
  lesson, which POPSIGN's mixed 1944×2592 / 1080×1920 video would have hit.
- `cli.ts` gains `--model`; `--width/--height/--fps` demoted to overrides.
- Python reference tree: 12 clips, one per label, seeded 42, 47.7 s. Face and
  pose detected on 1.00 of frames, hands 0.00–0.73.
- The parity sample comes from POPSIGN **train a–e**, not test: the test split's
  videos are gone (`popsign_cycle` deletes video once landmarks verify), and
  parity only needs identical inputs, not a particular split.

## 8. What this does not block

Nothing about POPSIGN extraction. `packages/sb-extract` uses the native C++
MediaPipe pipeline with no GL requirement, which is why it has already done
33,599 clips. The TS path is the thing that is blocked, and the honest route
back is a headless browser — which is also where §10.2's livestream mode has to
live, so that work would not be thrown away.
