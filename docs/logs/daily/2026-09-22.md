# 2026-09-22 — streaming confidence/reset architecture scoped, built, and run

Two live-inference plans from the user (per-architecture latency testing, and
a MediaPipe → streaming-model → LLM-reset pipeline) were checked against
`TODO.md` and `CLAUDE.md` before any code was written.

## 1. Architecture review

The streaming/reset idea turned out to already exist as an unscoped Backlog
remark (2026-09-19), and the LLM-reset role collides with §8's older,
differently-scoped LLM correction-layer idea (post-hoc near-synonym
correction, not a reset trigger) — both now share one open gap: neither
GISLR nor POPSIGN has sentence-level data to build a "next-word suggestion"
from. Findings fed back to the user:

- **BiLSTM cannot participate in frame-by-frame inference at all** — its
  backward pass has already read the whole future sequence, so there is no
  causal per-frame readout to expose. It stays a plan-1 latency/accuracy
  reference only (same rule as §4.1).
- **DNN has no state to "reset"** — it is exactly memory-free per frame
  (`sb.recognize.interp.models.LandmarkDNN`), so any external accumulator
  built on top of it, not the model, would need clearing.
- **The real blocker is calibration, not the reset mechanism.** Every
  streaming architecture here is trained with a loss at the LAST valid frame
  only — a raw hidden state at frame 15 was never supervised to produce a
  meaningful softmax. This has to be measured before deciding whether a
  per-frame-supervised retrain is actually necessary.
- Recommended staging: measure first on existing checkpoints (Phase A/B, no
  training), only retrain (Phase C) if that shows mid-sequence confidence is
  genuinely unusable, and keep the reset MECHANISM separate from the reset
  DECISION-MAKER (a rule-based threshold+hold trigger first, an LLM only
  once §8's data-source question is answered).

## 4. Two bugs found running the notebook for real, both fixed

- **`np.savez_compressed` silently appends `.npz`** to any filename that
  doesn't already end with it. The stream-construction cell's tmp path,
  `"<i>.npz.tmp"`, was actually written to disk as `"<i>.npz.tmp.npz"`, so
  the subsequent `os.replace` failed with `FileNotFoundError` looking for a
  file that was never created under that name. Fixed by naming the tmp file
  `"<i>.tmp.npz"` instead (already ends in `.npz`), verified the
  write/rename round-trips correctly.
- **The GPU parity assertion failed** (`gru`: 5e-4 max diff, over the 1e-4
  tolerance) — not a `RecurrentSession` bug. Reproduced directly: cuDNN
  dispatches a different kernel for one whole-sequence GRU/LSTM call than
  for a loop of single-frame calls, so floating-point error accumulates
  differently between the two even though they compute the same recurrence
  (5e-4 max diff on GPU over 200 real frames vs. 1.6e-6 on CPU with the same
  checkpoint). Fixed by running the parity check on CPU, where the
  computation is a plain step-by-step loop with no kernel-selection
  dependence — the actual test of whether the two agree. Models are moved to
  CPU for the check and back to `DEVICE` afterward.

## 5. Notebook run end to end (0 failures) and analyzed

All phases ran clean after the fixes above: 4 checkpoints loaded (`gru`
0.7291, `lstm` 0.7341, `cnn` 0.6688, `dnn` 0.6476 internal-val acc, matching
`five-arch-benchmark.md`), 30 synthetic streams built, Phase A/B/D all
completed.

**The first read of Phase A's results (position-binned confidence averaged
over every segment) looked like it confirmed the original worry** — `gru`'s
early/mid/late confidence was only 0.048/0.142/0.212, a slow climb that
would seem to justify the per-frame-supervised retrain (Phase C). Before
accepting that, split the aggregate by whether a segment starts fresh
(stream position 0, zero-initialized state) or carries over a prior sign's
un-reset state (positions 1-3, three of every four segments) — added as a
new §3b cell rather than just computed ad hoc, since it changes the
notebook's own conclusion:

| arch | fresh start (early→mid→late) | contaminated, no reset |
|---|---|---|
| `gru` | 0.161 → 0.421 → **0.584** | 0.010 → 0.048 → 0.088 |
| `lstm` | 0.190 → 0.397 → **0.503** | 0.016 → 0.074 → 0.137 |
| `cnn` | 0.193 → 0.386 → **0.518** | 0.020 → 0.089 → 0.187 |
| `dnn` (no state to contaminate) | 0.233 → 0.254 → 0.314 | 0.189 → 0.233 → 0.228 |

**A fresh start already accumulates strong, well-calibrated evidence** —
`gru`'s late-third confidence (0.584) matches the whole-video mean-true-
class-confidence numbers from `five-arch-benchmark.md` (0.59-0.61). The
last-frame-only-supervision worry that motivated this whole notebook is real
in principle but is not what these numbers are actually showing.
**Un-reset state contamination is** — a contaminated segment's own late-
third confidence (0.088) sits *below* a fresh segment's own early-third
(0.161), and `dnn` (no persistent state at all) shows almost none of this
gap, pinning the effect specifically on carried recurrent state.

This is consistent with, and explains, Phase B's boundary-effect numbers
(oracle reset cuts bleed-through 19.6→0.8 frames and re-acquisition latency
41.4→23.3 for `gru`) and Phase D's trigger sweep (`gru` beats `lstm` at
every threshold/hold setting, `tau=0.7/hold=5` a reasonable middle ground at
0.858 precision).

**Verdict: reprioritize Phase C down.** It is no longer the assumed
prerequisite — downgraded in `TODO.md` §11.2 from "next" to "optional
refinement, revisit only if a live reset-wired system still under-performs."
The actual lever is making reset a first-class part of any live inference
loop, and `RecurrentSession` already does this correctly (verified to 1e-6
against the batch computation on real data).
