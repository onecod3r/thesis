# 2026-08-23 — The 1st-place run dies at epoch 15 (twice); stopping conditions added

The first full run of the 1st-place port (TODO §4.2) finished 300 epochs in 2.0 h and
scored **0.7459** canonical — below the 0.7565 GRU, and nowhere near the 0.84–0.88 the
notebook set as a realistic single-model expectation. It is not a measurement of the
recipe: the run diverged at epoch 15 and spent its last 285 epochs training a dead model.

---

## 1. What happened

Run `1787483814` · `conv1d_transformer` · FP_118/xy · regime `fp-onecycle-300`.

| epoch | train loss | train acc | val acc |
|---|---|---|---|
| 14 | 2.009 | 0.715 | **0.746** ← best, and the checkpoint in `best.pt` |
| 15 | 5.788 | 0.027 | 0.017 |
| 16 | 5.526 | 0.007 | 0.025 |
| 65 | 5.039 | 0.044 | 0.071 |
| 299 | 4.543 | 0.148 | 0.179 |

`ln(250) = 5.5215`. From epoch 16 the training loss sits within 0.01 of it for ~45 epochs,
i.e. the model is emitting a uniform distribution over the 250 classes. It later claws back
to 17.9% as the cosine anneals the LR, and finishes there.

**Epoch 15 is not a coincidence.** It is `awp_start_epoch` *and*
`late_dropout_start_epoch` — the single step at which AWP (λ=0.2) and LateDropout (p=0.8)
both switch on.

### It is a gradient blow-up, not a NaN and not a plateau

The reference author's documented failure mode at `awp_delta: 0.2` is a NaN loss (~1 run in
5). This run never went NaN. Comparing `best.pt` (epoch 15) against `last.pt` (epoch 300)
shows what it did instead:

| tensor | epoch 15 | epoch 300 |
|---|---|---|
| `stem.weight` ‖w‖ | 16.1 | **223.6** |
| `stem_bn.running_var` ‖·‖ | 4.8 | **8467.6** |
| `stem_bn.bn.weight` (γ) ‖·‖ | 11.2 | 2.5 |
| `stages.0.conv1.bn.bn.weight` (γ) ‖·‖ | 11.7 | **0.22** |
| `stages.0.conv1.bn.bn.bias` (β) ‖·‖ | 1.22 | **0.004** |

The stem exploded 14×, and every BatchNorm behind it collapsed its scale toward zero to
suppress the resulting signal. Because BatchNorm makes the layer before it scale-invariant,
a 14× weight norm also divides the stem's *effective* learning rate by ~200 — the network
could not walk back out of the hole it fell into.

### Two causes, both fixable

1. **`grad_clip: 0.0`.** Faithful to the reference (its `clipvalue=1` is commented out) and
   fine without AWP. AWP takes its optimizer step from a gradient measured at a point where
   every weight tensor has been pushed 20% of its own norm *up* the loss surface — precisely
   where an unclipped update is most dangerous.
2. **AWP's adversarial forward was updating the BatchNorm running statistics.** That pass
   exists only to produce a gradient; the weights are restored immediately after. But a
   `model.train()` forward also writes its batch statistics into `running_mean`/`running_var`,
   so the statistics used at *eval* time were being fed activations from perturbed weights,
   twice per step. `stem_bn.running_var` = 8467 is that, accumulated. The reference's Keras
   AWP has the same flaw; it is a bug either way.

## 3. What changed in the code

- **`modules/model/optim.py`** — new `frozen_bn_stats(model)` context manager: holds every
  BatchNorm's running buffers still (`momentum = 0`) while still normalizing with batch
  statistics, so the adversarial forward cannot poison them. `train_fp.py` wraps AWP's second
  forward in it.
- **`modules/model/train_fp.py`** — stopping conditions, which the regime previously had none
  of by design ("fixed-length cosine — no early stopping"):
  - `collapse_ratio` / `collapse_patience` — val accuracy below 50% of the run's own best for
    3 consecutive epochs ends the run. Replayed against this run's history it stops at
    **epoch 18**, saving 282 epochs.
  - `es_patience` / `es_min_delta` — the ordinary plateau stop (30 epochs, +0.001), same
    semantics as `v2-plateau-300`. Generous on purpose: a one-cycle cosine earns real gains
    late, while the LR anneals.
  - Non-finite train or val loss ends the run immediately.
  - `meta.json` now carries `training.stop_reason` ∈ {completed, plateau, collapse, nan}
    alongside `early_stopped`; both counters are checkpointed, so a resumed run keeps them.
- **`src/config/gislr.firstplace.json`** — `grad_clip: 0.0 → 1.0`, plus the new stop keys and
  `stop_after_epoch`, each with a note explaining it against the failure above.
- **`src/gislr.1.models.firstplace.ipynb`** — §0.4 rewritten around what actually happened;
  §5 documents the stops; §6a marks the AWP/LateDropout switch epoch on every curve and warns
  when the best epoch lands at or before it; **new §7b** prints per-class best/worst, the
  confused-pair table and the confusion matrix from the cached predictions (no re-inference).

## 4. The re-run collapsed too — the guard worked, the diagnosis did not

Run `1787492560`, same config plus all three changes above:

| epoch | train loss | train acc | val acc |
|---|---|---|---|
| 15 | 2.063 | 0.697 | **0.7415** |
| 16 | 5.076 | 0.081 | 0.039 |
| 17 | 5.492 | 0.011 | 0.050 |
| 18 | 5.494 | 0.012 | 0.048 |

Stopped by `collapse` at epoch 18 after **9.1 minutes**, against 300 epochs and 2.0 h for
the same failure the first time. That part works exactly as intended.

But the fixes did not prevent the divergence — they softened it. Epoch-16 average loss is
5.076 against 5.788 before, and 5.076 vs ln(250)=5.52 implies the model is still near 2.1
for roughly the first **20 steps** of the epoch and dead after. A ~20-step runaway is not
what a single unclipped update looks like; gradient clipping was treating the wrong shape
of problem.

**What is still untested is the obvious thing**: epoch 15 switches on AWP (λ=0.2) *and*
LateDropout (p=0.8) simultaneously, and neither has ever been run alone. New notebook
**§5b** does that — three arms (`awp_delta: 0` / `late_dropout: 0` / control), same seed,
same data, each stopped at epoch 25, ~30 min total. Arms that collapse exit at ~18 on the
guard.

The arms use a new `stop_after_epoch` config key rather than lowering `epochs`, and the
distinction matters: the cosine one-cycle is laid out over `epochs`, so setting it to 25
would put epoch 15 at ~15% of peak LR and answer a different question. `stop_after_epoch`
ends the run while leaving the schedule alone.
